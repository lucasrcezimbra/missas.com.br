# Project Agent Instructions

This project uses **Ariad**.

Ariad is the canonical method. This repository contains a local Ariad instance, not the canonical Ariad documentation. All paths below are local to this repository.

The agent is the **Driver**. The human is the **Navigator**. The Driver operates the repository; the Navigator holds direction, product judgment, trade-offs, and acceptance.

## Project Summary

Missas.com.br is a Django web application that helps Catholic faithful find Mass and confession schedules for parishes in Brazil.

Core model hierarchy:

```text
State
  City
    Parish
      Location
      Contact
      Schedule
        Source
```

## Operating Principles

- Read relevant code and documentation before changing files.
- Preserve coherence between process, project, and product.
- For non-trivial work, plan before implementation.
- Use tests for behavior changes when practical.
- Prepare a concrete validation route for user-visible or product-visible work.
- Update documentation in the same cycle as the change when project memory changes.
- Stop at checkpoints and wait for Navigator confirmation.
- Do not silently absorb new scope. Capture it for later unless it blocks correctness or coherence.
- Prefer small, reviewable changes over broad unbounded edits.

## Django and Python Rules

- Use function-based views unless there is a strong reason not to.
- Use Django migrations generated by Django CLI; do not hand-write migrations.
- Avoid type hints in project Python code.
- Follow Ruff rules configured in `pyproject.toml`.
- User-facing strings should be Brazilian Portuguese; code identifiers and technical documentation should be English.
- Avoid useless comments that restate code. Comments should explain why.
- Never do database queries inside loops. Use `select_related`, `prefetch_related`, annotations, or bulk operations.
- Prefer real test backends and model-bakery over mocks when practical.
- Use mocks only for external services or expensive I/O boundaries.

## Frontend Rules

- Use Bootstrap 5, HTMX, and FontAwesome consistently.
- JavaScript is required; this project does not support no-JavaScript browsers.
- Avoid inline CSS. Use CSS classes and external stylesheets.
- Maintain responsive behavior for mobile users.
- For UI changes, run the app, take a Playwright screenshot at 1920x1080, and add it to PR comments.
- PR titles for UI changes must include `[render preview]`.

## Commands

All Python and Django commands must run through uv.

```bash
make install
make test
make lint
make coverage
make dev
uv run python manage.py migrate
uv run python manage.py runserver
uv run pytest
```

## Checkpoints

For non-trivial work, follow Ariad's lifecycle:

1. Read and orient.
2. Plan and stop for Navigator confirmation.
3. Implement.
4. Test and present automated evidence plus Navigator validation route.
5. Review refactoring and debt impact; stop for confirmation.
6. Update documentation and run coherence check.
7. Propose history action; stop before commit or push unless local policy says otherwise.

For trivial, low-risk work, compress checkpoints but still show what changed and how it was verified.

## History Policy

- Commit after a coherent story or meaningful change is validated and accepted.
- Ask before pushing to shared remotes.
- When a commit fails because of pre-commit, fix the reported issues before retrying.
- Commit messages should explain why, not only what.
